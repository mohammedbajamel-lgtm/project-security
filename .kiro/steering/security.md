# CloudSec AI Security Guardrails

## Least Privilege

- Never use AdministratorAccess for CloudSec AI application components.
- Avoid wildcard IAM actions/resources unless technically required and explicitly documented.
- Use scoped IAM roles and temporary credentials.
- Every IAM implementation must identify Principal, Action, Resource, Conditions, and trust relationship.
- Cross-account access must follow the approved design.

## AI Trust Boundary

Amazon Bedrock is an investigation and recommendation component, not an unrestricted AWS operator.

Required flow:

AWS Evidence → Bedrock → Structured Output → Schema Validation → Evidence/Citation Validation → Safety Validation Engine → Approved Remediation Playbook → Step Functions/Lambda/SSM → AWS API → Verification

Never:
- Give Bedrock AdministratorAccess.
- Allow Bedrock to directly execute arbitrary AWS API actions.
- Execute arbitrary commands generated by an LLM.
- Trust an AI-generated resource, event, identity, or conclusion without validating it against evidence.
- Allow confidence score alone to authorize a dangerous action.

## Remediation Safety

- Only predefined remediation playbooks may modify AWS resources.
- Remediation must be idempotent.
- Preserve required forensic evidence before disruptive containment.
- High-impact actions require human approval according to the approved design.
- Never automatically delete important production resources.
- If validation fails, fail safely and escalate.
- Every remediation must be followed by verification.
- An API success response alone does not mean the incident is resolved.

## Evidence

- Treat incoming security telemetry as untrusted input.
- Preserve evidence integrity.
- Encrypt sensitive evidence.
- Never unnecessarily log secrets, credentials, tokens, or sensitive evidence.
- AI conclusions must reference real evidence.
- Clearly distinguish confirmed evidence from inference.
- Reject unsupported/hallucinated events.

## Infrastructure

- Infrastructure must be managed through Terraform unless explicitly documented otherwise.
- Development resources must remain cleanup-friendly.
- Do not automatically run `terraform apply` without explicit approval.
- Do not introduce expensive AWS services without documenting the cost impact.
- Never hard-code credentials, secrets, account IDs, or sensitive configuration.

## Implementation Gate

A security-sensitive task is not complete merely because code was generated.

Before marking it complete:
1. Acceptance criteria must pass.
2. Required tests must pass.
3. IAM permissions must be reviewed.
4. Failure paths must be tested where applicable.
5. Security implications must be checked.
6. Manual verification instructions must be provided.

At manual review checkpoints defined in `tasks.md`, stop before continuing.
